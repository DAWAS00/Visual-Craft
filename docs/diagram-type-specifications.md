# Five diagram types: specification and tasks

Proposal, 2026-11-19; status as of 2026-11-20 is in [Status](#status-2026-11-20) below. The [UI spec](diagram-ui-spec.md) and the [implementation plan](diagram-implementation-plan.md) cover the flowchart editor; this file adds the typed diagrams and their tasks.

## Summary

This specification covers **Basic Flowchart**, **UML Class Diagram**, **UML Sequence Diagram**, **Entity Relationship Diagram** (ERD) and **UML Use Case Diagram**.

Flowcharts are Boards and keep the Board layers and collaboration path. Class, Sequence, ERD and Use Case are **typed diagrams**. Each page holds at most one typed model, and canvas layers are generated from it. Typed diagrams are native-only in this release: no live sessions, no branch merge or update.

## Decisions

- **D0 Scope (decided 2026-11-19).** Flowchart first, then Class and ERD, then Sequence. The owner asked for all four types in the program, so the UI spec's first-release scope (its D3 and non-goals) now ends with the flowchart slices, and the typed slices (8–14 below) follow.
- **D1 Page types.** A page is a Board page or a typed page (`class`, `sequence`, `erd`, `useCase`). A typed page owns at most one model; its type is fixed at creation.
- **D2 Layers on typed pages.** A typed page holds only generated layers. Ordinary layer creation is refused on it.
- **D3 Archive compatibility (whole file).** The top-level header is format version 2 whenever any typed record exists in the current document, a saved version or a branch. Saving scans all three. Files with no typed record keep version 1. Older readers refuse version 2 with an "update FigCraft" message. A version-2 reader that meets an unsupported record schema anywhere in the archive refuses the whole file. Fixtures: (a) a plain current document with a typed page only in a saved version; (b) a plain current document with an unsupported schema only in a branch. This is a craft-libs task before the first typed slice.
- **D4 Unsupported schema.** Refuse the file (D3). No read-only fallback layers are persisted.
- **D5 Semantic IDs and the allocator.** Each typed element, row, link and message has a numeric ID from one allocator per file. Branch tabs and main share it by reference. The allocator is outside the undoable snapshot, so undo, redo, version restore and page deletion never lower it. It is saved in the version-2 header as the largest ID ever issued in the file. Version-1 resaves drop it; the non-reuse guarantee holds for saves by readers that write version 2. Duplicating a page allocates fresh IDs and remaps every reference inside the copy. Offline `file.import` of a typed page allocates fresh IDs and remaps every reference. Pasting typed content into another model is refused in v1. A dangling reference found at load refuses the file.
- **D6 Generated layers.** Layers are regenerated from the model after each successful typed command and on load. Each carries its semantic ID and role (card, row, link, lifeline, activation, message, label, marker; for Use Case also figure and boundary). Selection and hit targets map through (page, semantic ID, role).
- **D7 Generic edits on generated layers.** Transform, text editing, Delete, cut, paste, nudge and align are refused on generated layers with a message to use the typed command. Selection, hover, zoom and pan are allowed.
- **D8 Transaction.** A typed command is refused while any ordinary interaction (text edit, drag, vector edit) is open; the UI ends it first. Dispatch checks the command that would actually run, through `edit.repeat` and nested `command.batch` steps, before it ends a text preview or changes anything else. A typed draft stays outside the document until commit. Commit dispatches one command that validates on a copy and changes nothing if refused. One command is one undo step. Preview, cancel, no-op and rejected edits add no step.
- **D9 Export.** One engine-owned export path serves `file.export`, the egui export and the CLI's `export_file`. Selection expansion (D10) resolves the drawn set first, and bounds, scale and fixed width or height are computed from that resolved set.
- **D10 Selection expansion.** One pass, not recursive. On a Use Case page a selected subject first adds its member use cases to the selection, and a subject is drawn as context around any resolved member without adding anything else. An originally selected card or participant adds each incident edge (link or message) **and both endpoints of that edge**. An originally selected link or message adds its two endpoints. Example: with `A—B—C` and only `A` selected, the resolved set is `A`, `A—B`, `B`. That set is used for drawing and for sizing. The fixed-width export of this case is a regression test.
- **D11 Live sessions.** Typed pages are refused in any tab that is connected, connecting, reconnecting or resumable. Guarded: sharing, hosting and publishing (across all pages, empty typed pages included); `file.import` of a typed page; `version.restore` of a snapshot with a typed model; remote replacement of a typed tab. Two separate tests for the history path, because hosting itself refuses first: (i) the host command refuses before the transport starts when local history holds a typed snapshot; (ii) with a controlled pre-welcome session fixture (history present, welcome not yet received), undo and redo refuse a typed candidate and leave the history entry in place. A join that opens a separate Board tab still works.
- **D12 Branch merge and update.** Refused for files with a typed record anywhere in the archive, checked before the merge planner is called.

## Diagram specifications and functions

### 1. Basic Flowchart (a Board)

**Create from zero.** Place a Start terminator, add process and decision shapes, and connect them with directed arrows. Label decision branches and connect a retry branch back to an earlier step.

| Area | Specification |
| --- | --- |
| Objects | Terminator, process rectangle, decision diamond, directed connector with an optional label. |
| Functions | `board.shape`, `board.addConnected` (`shape`, `label`; slice 1), `board.connector`, `board.label`, `board.reattach`, `board.reshape`. New: `board.insertFlowchart` (text import, one undo step) and `board.arrangeDiagram` (`direction: LR|TB`, one undo step). |
| Clearance rule | Immediately after Arrange, return channels keep the router's clearance. After a manual move, endpoints and labels re-attach with no clearance guarantee. |
| Acceptance | Build **Review → Approved? → Ship / Revise** with **Revise → Review**, visually and from text. Arrange LR and TB. Move the decision; labels and connectors still attach. Reopen and export with both labels visible. |

### 2. UML Class Diagram (typed, page kind `class`)

**Create from zero.** Add a class, interface or enumeration, type its members as UML text on the card or in the panel, and connect it to another classifier, or drag a connected element out of it. A preview: it is saved as format version 2 (slice 8) once the craft-libs change lands; until then saving it is refused.

| Area | Specification |
| --- | --- |
| Objects | Classifier cards: class (with an abstract flag), interface, enumeration; name, optional stereotype. Attributes `[vis] [static] name [: Type] [[multiplicity]] [= default]`; operations `[vis] [static] [abstract] name(p: T, …) [: Return]`; literals (enumerations only). Visibility `+ - # ~`. |
| Relationships | **Association** (role, multiplicity and navigability at each end; a self-association is a loop off the card's top-right corner). **Aggregation** / **Composition**: `ends[0]` is the whole, a hollow / filled diamond; the whole's multiplicity, if given, is `1` or `0..1` for a composition. **Generalization**: same kind both ends, never an enumeration, acyclic. **Realization**: class or enumeration → interface, dashed shaft and hollow triangle. **Dependency**: dashed open arrow, optional label. |
| Duplicates | A plain association compares its unordered ends with their roles and multiplicities (so employer / employee between the same pair is allowed); other kinds compare kind and ordered ends. Composition is acyclic across classifiers (stricter than UML). |
| Editing contract | An omitted field stays, `null` clears. A kind change only where nothing is lost: among association, aggregation and composition; class ↔ interface. Swapping an aggregation's or composition's ends reverses which side is the whole. |
| Caps | 200 classifiers, 100 members per classifier and 2,000 in all, 8 parameters per operation and 1,000 in all, 1,000 relationships, 200 characters per text, 10,000 generated layers, coordinates within ±1,000,000, cards at least 24 apart; enforced on decode as well. |
| Geometry | Fixed-height rows from one pure layout shared by the renderer and the interface's hit-testing; diamonds, triangles, arrows and dashed shafts are generated vector paths, so they export. |
| Functions | `diagram.class.addClassifier {kind?, name, x?, y?, abstract?}`; `updateClassifier {id, name?, kind?, abstract?, stereotype?, showAttributes?, showOperations?}`; `move`; `resize`; `addMember {classifier, compartment, text \| fields, after?}`; `updateMember {id, text \| fields}`; `moveMember {id, before \| after}` (within its compartment); `removeMember`; `connect {kind, from, to, ends?, label?}`; `addConnected {source, relation, kind, direction, wholeEnd?, name, x?, y?}`; `updateLink {id, kind?, ends?, label?}`; `swapEnds`; `remove {ids}` (cascades its relationships); `check`; `read`. Every change is one undo step; a refusal or no-op adds none. |
| Interface | A floating panel with picture tools (Select, Class, Interface, Enumeration; the six relationships), the selected card (kind, abstract, name, stereotype, each member as UML text with visibility, up, down, remove) or relationship (kind among the association kinds, both ends, label, swap). On the canvas: press selects a card and its row, drag moves, a tool places or joins, a double-click or Enter types over a row, Alt+Shift+A / Alt+Shift+O add an attribute / operation (only on a Class page with a card selected), Insert adds a row after the selected one, `[` and `]` step through cards and relationships, arrows move (Shift: 1), Alt+arrows resize, Delete removes. A "+" handle on the selected card drags out a new connected element from a chooser of only the valid choices. |
| Acceptance | The **Library loans** template: `Library` ◆— `Shelf`, `Shelf` ◇— `Book`, `Member` 1 — 0..* `Loan` (roles `borrower` / `loans`), `Loan` → `Book`, `Book` realizes `Borrowable`, `PremiumMember` generalizes `Member`, `Loan` depends on `Clock`, `Loan` — `LoanStatus` (`Open`, `Returned`, `Overdue`): all six kinds, no unfinished parts. |

Notation follows UML 2.5.1. [OMG UML specification](https://www.omg.org/spec/UML/2.5.1)

### 3. UML Sequence Diagram (typed, page kind `sequence`)

**Create from zero.** Add participants across the top, then insert messages in the order they occur. Drag a message to change its place in the interaction.

| Area | Specification |
| --- | --- |
| Objects | Participants (ordered), messages (ordered), activations. Message kinds: call, async message, reply. |
| Geometry | A participant's centre is its header's centre. Headers sit left to right with a 40-unit gap after the widest header in the row. Lifelines start one line below the tallest header and end 40 units below the last event. Each event takes a row at least 48 units high; when the measured label line needs more, every row grows by the same amount (the formula is in the [Sequence plan](sequence-diagram-plan.md)). A self-message loops 32 units right of its lifeline, or 12 right of its activation bar when that is further. Labels longer than 40 characters are kept whole in the model and drawn truncated with an ellipsis. |
| Endpoints | A message has sender and receiver participant IDs. A self-message has equal endpoints; its kind is stored separately. Arrows attach to the activation bar's edge when one is present at that event, otherwise to the lifeline. |
| Activations | An activation has a participant ID, a start message ID and an end message ID on that participant's lifeline. Nesting is allowed; each nesting level draws 6 units further right. |
| Replies | A reply's `of` is optional. A linked reply requires `of` to be an existing call with reversed endpoints and a later event. An unlinked reply is allowed. |
| Validation | One validator runs on create, move, endpoint or kind update, and load. It checks that each activation starts before it ends, no two activations on one participant cross, and each linked reply follows its call with reversed endpoints. A failing change is refused before mutation. |
| Functions | `diagram.sequence.addParticipant {name, after?}`; `diagram.sequence.moveParticipant {id, before?|after?}`; `diagram.sequence.addMessage {kind, from, to, label, after?|before?, of?}`; `diagram.sequence.updateMessage {id, kind?, from?, to?, label?, of?}`; `diagram.sequence.moveMessage {id, before?|after?}`; `diagram.sequence.removeMessage {id}`; `diagram.sequence.removeParticipant {id}`; `diagram.sequence.setActivation {participant, start, end}` (result: activation ID); `diagram.sequence.removeActivation {id}`. |
| Deletion | Removing a participant removes its messages and their activations in one step. Removing a message removes the activations that start or end on it and the replies that reference it, in one step. |
| Acceptance | Participants `Requester`, `Review service`, `Store`. Messages in order: a self-call on `Review service`; then `m1` call `Review service` → `Store`; `m2` and `m3` async `Review service` → `Store`; `m4` reply `Store` → `Review service` with `of: m1`. Activations on `Store`: A = `[m1, m4]`, B = `[m2, m3]` (nested, legal). Legal reorder: move `m1` above the self-call. Rejected, each unchanged: move `m4` above `m1` (reply before its call); move `m1` after `m2` (A would start inside B and end after it: crossing; the reply order still holds, so only the crossing rule fires). Reorder participants, save, reopen, verify IDs, order and activations. |

Notation follows UML 2.5.1. [OMG UML specification](https://www.omg.org/spec/UML/2.5.1)

### 4. Entity Relationship Diagram (typed, page kind `erd`)

**Create from zero.** Add entities, enter their columns, and connect related entities. Set the cardinality at each end and whether the foreign key is nullable.

| Area | Specification |
| --- | --- |
| Objects | Entity cards with ordered columns. A column has ID, name, type label and nullability. An entity has at most one primary-key column. |
| Relationship model | A relationship stores both ends by entity ID, each with a role-named cardinality: `zero or one`, `exactly one`, `zero or many`, `one or many`. |
| Two command forms | **Entity-only** (no FK): `connect` requires both `fromCardinality` and `toCardinality`. **FK-bound**: `connect` takes `fk: {source column, target column}` and `fromCardinality` (the many side); `toCardinality` is refused, because the one side is derived. |
| Derived cardinality | For an FK-bound relationship the one-side cardinality is derived from the FK column's nullability: nullable gives `zero or one`, non-nullable gives `exactly one`. It is read-only: `updateCardinality` refuses it. A nullability change recomputes it in the same undo step. The conflicting pair cannot be written. |
| Foreign key | An FK binding stores the source column ID (many side) and the target primary-key column ID (one side). `diagram.erd.unbindForeignKey {relationship}` removes only the binding; the relationship becomes entity-only and both its cardinalities must then be stored. |
| Primary key | A primary-key column cannot be nullable. Changing the PK is refused while a binding references the current PK. |
| Routing | Ports are on a card's left or right edge at the row's midpoint, or at the card's vertical middle for an entity-only link. **Side-by-side** cards: the port sides face each other; if the two row anchors have equal Y, the route is one straight horizontal segment; otherwise it is horizontal–vertical–horizontal through a lane in the gap between the cards. **Stacked with overlapping horizontal extents**: both ports are on the same exterior side (the side away from the overlap, chosen as right if the overlap centre is left of the cards' centre, otherwise left), and the lane is 24 units outside the cards on that side, so no terminal segment crosses a card. **Stacked without overlap**: the facing side rule applies and the lane is the midpoint of the horizontal gap; if that lane crosses a card, it moves 24 units outward and the route is checked again. Markers sit on the terminal segments. |
| Edit rules | Deleting the FK source column unbinds the relationship. Deleting a referenced PK is refused until the binding is removed. Renaming and reordering keep IDs, so bindings follow columns. |
| Functions | `diagram.erd.addEntity {name, x, y}`; `diagram.erd.moveEntity {id, x, y}`; `diagram.erd.addColumn {entity, name, type, nullable, after?}`; `diagram.erd.updateColumn {id, name?, type?, nullable?}` (a nullability change recomputes the derived end); `diagram.erd.moveColumn {id, before?|after?}`; `diagram.erd.setPrimaryKey {column}`; `diagram.erd.connect` (two forms above); `diagram.erd.updateCardinality {relationship, end, cardinality}` (refused for a derived end); `diagram.erd.unbindForeignKey {relationship}`; `diagram.erd.removeColumn {id}`; `diagram.erd.removeEntity {id}` (removes its relationships in one step). |
| Acceptance | `Customer` (PK `id`); `Order` (PK `id`, columns `customer_id` and `total`). FK-bound `Order.customer_id` → `Customer.id` with `fromCardinality` `zero or many` at `Order`; the `Customer` end is derived `exactly one`. Reorder `Order` so `total` comes first: the line stays on `customer_id`. Rename `customer_id`: the line stays. Make `customer_id` nullable: the `Customer` end becomes `zero or one`, in one step. Refused and unchanged: `updateCardinality` on the derived end. Export cases with both markers each time: side-by-side with equal row heights; side-by-side with unequal row heights; stacked with overlapping extents (`Customer` above `Order`); stacked and staggered without overlap; side-swap after `moveEntity`. |

The first release authors and exports the diagram. SQL generation, composite keys and Chen notation are later work. [Visual Paradigm ERD guide](https://circle.visual-paradigm.com/docs/database-design-engineering/database-designers-guide/how-to-draw-an-erd/)

### 5. UML Use Case Diagram (typed, page kind `useCase`)

Added 2026-11-19 at the owner's request, from the owner's [design proposal](use-case-diagram-implementation.md) (workflow research and the Room booking example) and a plan reviewed by Codex in five rounds. Notation follows UML 2.5.1; the symbols, example and UI are original.

| | |
|---|---|
| Elements | **Actor** (person, drawn as a stick figure, or external system, a rectangle with «actor»); **use case** (ellipse) with ordered, named extension points (names on one use case have distinct `str::to_lowercase()` results); **subject** (system boundary, a rectangle). Several subjects side by side, no nesting. A use case belongs to at most one subject and may have none while drafting. |
| Relationships | **Association** actor–use case, undirected, drawn either way, stored actor-first, optional multiplicities by role. **Include** including → included. **Extend** extending → base at 1–8 extension points owned by the base, optional condition. **Generalization** specific → general, actors and use cases in separate hierarchies. No self links, no repeats per (kind, ends), and include, extend and both generalizations stay acyclic. |
| Geometry | Sizes are stored with each element's measured minimum, so validity never depends on the fonts of the machine that opens a file. A member use case stays 16 units inside its subject; actors and non-members stay 16 outside every subject; actor and use case boxes stay 24 apart, so every link has visible length; subjects don't overlap. Moving a subject moves its members; resizing it does not. |
| Drafting | `diagram.useCase.check` reports, never refuses: an unassigned use case, an empty subject, an actor with no association of its own or of an actor it specialises, a use case no actor reaches. |
| Commands | `diagram.useCase.addSubject`, `addActor`, `addUseCase`, `updateElement`, `move`, `resize`, `setSubject`, `addExtensionPoint`, `updateExtensionPoint`, `moveExtensionPoint`, `removeExtensionPoint`, `connect` (Extend may create a point on the base in the same step), `addConnected` (new element plus link in one step, named by direction: association, include, extension, parent, child), `updateLink`, `remove {ids}`, `check`. |
| Model | `figcraft_doc::use_case`: newtype IDs, a link enum whose variants hold only valid endpoint kinds, one `validate` and `check`, `UseCaseError` per rule. The format crate calls `validate` on every decoded record, and a decode error in a typed record refuses the whole version-2 file. |
| Acceptance | **Room booking** subject with `Reserve room` (point `Before total`), `Check availability`, `Apply member discount` and `Reserve meeting room`; actors `Guest` and `Member` outside. Guest–Reserve room association (drawn from the use case); Reserve room include Check availability; Apply member discount extend Reserve room at `Before total` if `member is eligible`; Member generalizes to Guest; Reserve meeting room generalizes to Reserve room. `check` reports nothing. Refused and unchanged: actor–actor association, an include from an actor, a mixed generalization, include and generalization cycles, a self include, a repeated include, an Extend without points or with another case's point, removing a referenced point, an actor inside a subject, two actors closer than 24. |

Later (slice 17): Dependency, notes and their attachments, packages, business variants, and scenario steps.

## Shared implementation and delivery

1. **Format first (craft-libs).** Land D3 in the shared format library, file-wide, with fixtures (a) and (b) and a test that the 0.18.1 reader refuses a version-2 file and still opens a version-1 file.
2. **Create and store.** `file.newDiagram {type: flowchart|class|sequence|erd}`, keeping `name` and `template`. Flowchart creates a Board; the others create a typed page at model version 1. The default type and the staged Mind Map option are unchanged.
3. **Commands.** Typed commands are `spec!`-registered, validate IDs and the active page before mutation, and return created IDs. `diagram.read {page}` returns IDs and order for CLI and MCP callers. The junk-parameter sweep covers typed commands on typed pages.
4. **Render from the model.** One renderer maps the model to layers; export uses it through the engine-owned path (D9).
5. **Live and merge gate.** Tests: a typed page refused on share, host, publish, import, version restore and remote replacement; the host command refuses before transport when history holds a typed snapshot; undo and redo refuse a typed candidate in a controlled pre-welcome fixture and keep the history entry; a live Board refuses to gain a typed page; merge and update refused for typed files. Keep the two-client flowchart test.
6. **Deliver in order.** (a) Finish Flowchart Board slices. (b) Format (D3). (c) Typed core: schema, allocator (D5), generated layers (D6), transactions (D8), export (D9), live gate (D11–D12), with an end-to-end **Class** slice. (d) **ERD** on the shared card, row and routing primitives. (e) **Sequence** with its fixed layout and validator.
7. **Verify each type.** For each acceptance example: creation, edit, undo and redo, save and reopen, page export and selection export, and a rejected edit that leaves the model unchanged. Run each command through the UI and the headless entry point. Run the workspace and WebAssembly checks before marking a slice done.
